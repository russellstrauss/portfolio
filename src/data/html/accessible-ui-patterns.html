Accessible UI Patterns

Reusable, accessible UI patterns ensure consistency and reduce development time while maintaining high accessibility standards. These patterns have been tested and validated for accessibility compliance.

Navigation Patterns

Main Navigation

  • Use semantic <nav> element
  • Provide skip links to main content
  • Ensure keyboard navigation works logically
  • Use ARIA labels for landmark regions
  • Provide breadcrumbs for deep hierarchies
  • Ensure mobile menu is keyboard accessible

Breadcrumbs

  • Use ordered list structure
  • Provide "You are here" context
  • Make current page clear (not a link)
  • Use proper separators (visually and in markup)

Form Patterns

Text Input

  • Always associate labels with inputs
  • Place labels above or to the left of inputs
  • Provide helpful placeholder text (but don't rely on it alone)
  • Show required field indicators
  • Provide inline validation feedback
  • Group related fields with fieldset/legend

Error Handling

  • Identify errors clearly (not just with color)
  • Describe errors specifically
  • Provide suggestions for correction
  • Associate error messages with form fields using aria-describedby
  • Allow users to review and correct before submission

Select/Dropdown

  • Use native select when possible
  • For custom selects, ensure full keyboard support
  • Provide clear labels
  • Support type-ahead functionality
  • Ensure options are announced by screen readers

Modal/Dialog Patterns

  • Use proper dialog/role="dialog"
  • Set initial focus to first focusable element
  • Trap focus within modal
  • Provide close button (X) and Escape key support
  • Use aria-modal="true"
  • Provide aria-label or aria-labelledby
  • Return focus to trigger element when closed
  • Prevent background scrolling

Tab Patterns

  • Use proper ARIA roles (tablist, tab, tabpanel)
  • Manage focus appropriately
  • Support arrow key navigation
  • Use aria-selected to indicate active tab
  • Associate tabs with panels using aria-controls
  • Ensure all content is keyboard accessible

Accordion Patterns

  • Use proper heading structure
  • Use button elements for triggers
  • Indicate expanded/collapsed state with aria-expanded
  • Associate content with trigger using aria-controls
  • Support keyboard navigation (Enter/Space to toggle)
  • Allow all to be expanded simultaneously (unless mutually exclusive)

Data Table Patterns

  • Use proper table structure (table, thead, tbody, th, td)
  • Associate header cells with data cells
  • Use scope attribute for simple tables
  • Use headers/id for complex tables
  • Provide table captions for context
  • Make tables responsive (consider mobile alternatives)
  • Ensure keyboard navigation works

Button Patterns

Primary Actions

  • Use semantic <button> element
  • Provide clear, descriptive labels
  • Indicate button state (disabled, loading, etc.)
  • Ensure sufficient size for touch targets (44x44px minimum)
  • Provide visual and non-visual feedback

Icon Buttons

  • Always provide text label (visually hidden if needed)
  • Use aria-label for icon-only buttons
  • Ensure icons are recognizable and consistent
  • Provide tooltips for additional context

Loading States

  • Announce loading state to screen readers
  • Use aria-live regions for dynamic content
  • Provide progress indicators
  • Ensure loading doesn't trap keyboard focus
  • Allow users to cancel long operations

Search Patterns

  • Provide clear search label
  • Include search button with descriptive text
  • Announce search results to screen readers
  • Provide clear "no results" messaging
  • Support keyboard navigation of results
  • Allow users to clear search easily

Pagination Patterns

  • Use proper link structure
  • Provide "Previous" and "Next" labels
  • Indicate current page clearly
  • Provide page number information
  • Support keyboard navigation
  • Consider "Jump to page" functionality for many pages

Carousel/Slider Patterns

  • Provide previous/next controls
  • Indicate current slide position
  • Allow users to pause auto-advance
  • Support keyboard navigation
  • Ensure all content is accessible (not just visible slide)
  • Provide alternative navigation method

Tooltip Patterns

  • Use aria-describedby to associate tooltip with element
  • Ensure tooltip is keyboard accessible
  • Don't rely on hover alone (provide click/tap alternative)
  • Keep tooltip text concise
  • Ensure tooltip doesn't obscure important content

Best Practices for All Patterns

  • Test with keyboard-only navigation
  • Test with screen readers
  • Ensure proper focus management
  • Provide clear visual and non-visual feedback
  • Document keyboard shortcuts
  • Maintain consistency across the application
  • Follow WCAG 2.1 Level AA standards
