Accessibility Checklists

Use these checklists to ensure your web projects meet accessibility standards. These can be integrated into your development workflow, design reviews, and quality assurance processes.

Pre-Development Checklist

  • Accessibility requirements defined in project scope
  • Target conformance level established (WCAG 2.1 AA recommended)
  • Accessibility testing tools selected
  • Team members trained on accessibility basics
  • Accessibility included in design system/component library
  • Accessibility review process defined

Design Checklist

Visual Design

  • Color contrast meets WCAG AA (4.5:1 for normal text, 3:1 for large text)
  • Information not conveyed by color alone
  • Focus indicators are visible and clear
  • Touch targets are at least 44x44 pixels
  • Text is readable (minimum 16px, appropriate font choice)
  • Design works at 200% zoom
  • Design compatible with high contrast mode

Content Design

  • Clear heading hierarchy planned
  • Navigation structure is logical
  • Form labels and instructions planned
  • Error states designed
  • Alternative text strategy defined
  • Multimedia accessibility planned (captions, transcripts)

Development Checklist

HTML Structure

  • Semantic HTML elements used appropriately
  • Single h1 per page
  • Proper heading hierarchy (no skipped levels)
  • Landmark regions used (header, nav, main, aside, footer)
  • Lists used for list content
  • Language declared on html element

Images

  • All images have alt attributes
  • Decorative images have empty alt=""
  • Alt text is descriptive and contextual
  • Complex images have detailed descriptions
  • Images of text are avoided when possible

Forms

  • All inputs have associated labels
  • Required fields are clearly indicated
  • Fieldset/legend used for related fields
  • Error messages are clear and specific
  • Errors are associated with form fields
  • Form validation is accessible

Links and Buttons

  • Link text is descriptive and meaningful
  • Buttons have clear labels
  • All interactive elements are keyboard accessible
  • Focus indicators are visible
  • No keyboard traps
  • Skip links provided for main content

Keyboard Navigation

  • All functionality available via keyboard
  • Logical tab order matches visual order
  • Focus management implemented for dynamic content
  • Standard keyboard shortcuts supported
  • Custom components support keyboard interaction

ARIA

  • ARIA used only when HTML isn't sufficient
  • ARIA labels and descriptions provided where needed
  • ARIA roles used for custom components
  • ARIA states updated dynamically
  • ARIA tested with screen readers

Content Checklist

  • Content is written clearly and simply
  • Headings organize content logically
  • Lists used for sequential or related items
  • Links are descriptive (not "click here")
  • Abbreviations explained on first use
  • Language changes indicated
  • Videos have captions
  • Audio has transcripts
  • Documents are accessible (PDFs, Word docs)

Testing Checklist

Automated Testing

  • Lighthouse accessibility audit run
  • axe DevTools scan completed
  • WAVE evaluation performed
  • HTML validation passed
  • No critical automated errors

Manual Testing

  • Full keyboard navigation tested
  • Screen reader tested (at least one)
  • Tested at 200% browser zoom
  • Tested with browser default font sizes
  • High contrast mode tested
  • Color blindness simulator used
  • Mobile device tested

User Testing

  • People with disabilities included in testing
  • Core user journeys tested
  • Feedback collected and addressed
  • Multiple assistive technologies tested

WCAG 2.1 Level AA Quick Checklist

Perceivable

  • Text alternatives for non-text content
  • Captions for prerecorded video
  • Audio description or media alternative for video
  • Information and structure not conveyed by presentation alone
  • Contrast ratio of at least 4.5:1 for normal text
  • Text can be resized up to 200%
  • Images of text avoided (except for logos)

Operable

  • All functionality available via keyboard
  • No keyboard traps
  • Timing adjustable (where applicable)
  • Pause, stop, hide for moving/blinking content
  • No content that flashes more than 3 times per second
  • Skip links or mechanisms to bypass blocks
  • Page titles are descriptive
  • Focus order is logical
  • Link purpose clear from link text
  • Multiple ways to find pages
  • Headings and labels are descriptive
  • Focus indicators are visible

Understandable

  • Language of page is identified
  • Language changes are identified
  • Navigation is consistent
  • Components with same functionality are identified consistently
  • Changes of context are not triggered automatically
  • Labels or instructions provided when content requires input
  • Error identification provided
  • Labels or instructions provided for errors
  • Error suggestions provided
  • Error prevention for legal/financial transactions

Robust

  • Valid markup
  • Name, role, value for all UI components

Pre-Launch Checklist

  • All automated tests passing
  • Manual testing completed
  • User testing with people with disabilities completed
  • Known issues documented with remediation plan
  • Accessibility statement prepared
  • Team trained on accessibility maintenance
  • Monitoring process established

Ongoing Maintenance Checklist

  • Regular accessibility audits scheduled
  • New features tested for accessibility
  • User feedback monitored and addressed
  • Accessibility included in code reviews
  • Team kept updated on accessibility best practices
  • Accessibility metrics tracked
  • Documentation maintained

Accessibility Statement Template

Your accessibility statement should include:

  • Commitment to accessibility
  • Standards followed (WCAG 2.1 Level AA)
  • Current accessibility status
  • Known limitations
  • Feedback and contact information
  • Date of last review

Use these checklists throughout your project lifecycle to ensure accessibility is built in from the start and maintained over time.
